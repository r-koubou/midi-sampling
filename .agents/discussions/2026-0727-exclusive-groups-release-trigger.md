# 排他グループとリリーストリガーの後付け可能性

- 実施日: 2026-07-27
- 種別: ディスカッション（実装・ファイル変更なし）
- 関連仕様: `.agents/specs/sampling_implementation.md`、`.agents/specs/postprocess_implementation.md`

---

## 1. 議題

将来 SFZ / UVI Falcon `*.uvip` へのエクスポートへ対応する際、現行のマニフェスト設計では表現できないレアケースが2件ある。

1. **グルーピング**: ドラムのオープンハイハットとクローズドハイハットのような排他的（choke）な関係をどう表現するか。
2. **リリースをトリガーに別のサンプルが鳴る音色**: ある音色のリリースフェーズ終了時に別サンプルをトリガーする挙動。

問いは「現行実装のままサンプリング作業を進めても、後から（既存マニフェストの変更を伴わずに）対応できるか」。

---

## 2. 結論

**どちらも後付けで対応可能。既存マニフェストの書き換えも再サンプリングも不要。サンプリング作業は現行実装のまま進めてよい。**

根拠は、2件とも**録音内容に一切影響しない純粋なメタデータ**である点にある。

| | 録音時に決まるもの | 後から決められるもの |
|---|---|---|
| 排他グループ | （なし） | グループ番号、choke対象 |
| リリーストリガー | 別サンプルの**録音そのもの** | どのサンプルが誰のリリースで鳴るかという**関係** |

- 排他制御はサンプラー再生時の発音停止であり、収録波形・送信MIDI・マッピングのいずれにも影響しない。1音ずつ `inter_sample_wait` を挟んで収録するため、収録中に choke が発生することもない。
- リリーストリガーで必要なのは「別サンプルを追加で録る」ことであり、既存音色の録り直しではない。追加分は新しい `id` の `sampling_definition` として後から足せる。既存の `recorded/<tone-id>/` は無傷のまま。

---

## 3. 唯一の制約: 情報の置き場所

現行設計には、マニフェストを後から編集すると連鎖的に破綻する箇所が2つある。

1. `sample_manifest.provenance.resolved_definition_sha256`
   不一致で `audit` が `definition_changed`（要再サンプリング）と判定する（サンプリング仕様 §17.3）。
2. `postprocess_manifest.provenance.source_manifest_sha256`
   source マニフェストの**バイト列**に対する SHA-256（ポストプロセス仕様 §10.3）。1バイトでも触ると派生成果物が `source_changed` 扱いになる。

したがって、**「録音済みマニフェストに後からグループ情報を追記する」解法だけは採ってはならない。** これさえ避ければ後付けは安全。

### ハッシュ側は既に保護されている

`ResolvedDefinitionHasher.build_payload()`（`src/midi_sampling/sampling/hashing/resolved_definition_hasher.py`）は明示的なホワイトリスト構築であり、`sampling_definition` にフィールドを追加しても `build_payload` に書き足さない限りハッシュは変化しない。仕様 §16.4 が表示用 `name` を対象外にしているのと同じ扱いにできる。

## 4. 推奨設計: エクスポート用の第3レイヤー

両課題はいずれも「サンプル**間**の関係」であり、`sampling_definition`（1音色 = 1組の Bank Select / Program Change による均質な収録単位、§7.3）が表現すべき概念ではない。将来は以下の3層構成を想定する。

```text
recorded/<tone-id>/manifest.yaml     kind: sample_manifest       録音の事実（不変・自動生成）
processed/<tone-id>/manifest.yaml    kind: postprocess_manifest  加工の事実（不変・自動生成）
instrument.yaml                      kind: instrument_definition 楽器としての構成（人が手書き・後から追加）
        ↓
    sfz / uvip / nki
```

イメージ:

```yaml
schema_version: 1
kind: instrument_definition

sources:
  - manifest: processed/sc8850-drums-1/manifest.yaml

exclusive_groups:
  - name: hihat
    members:
      - root_note: 42   # closed
      - root_note: 44   # pedal
      - root_note: 46   # open

release_triggers:
  - trigger_of: { tone: gtr-sustain }
    plays:      { tone: gtr-fret-noise }
```

- `root_note` / `key_low` / `key_high` は既にマニフェストの `mapping` に記録済みのため、後発の定義ファイルから既存サンプルを一意に指し示せる。
- ファイル名の逆解析は不要であり、サンプリング仕様 §24「ファイル名からマッピング情報を逆解析する設計にしない」に抵触しない。
- この配置ならサンプリング側・ポストプロセス側のプログラムは複雑化しない。増える複雑さはエクスポータ内に閉じる。
- ただしこの層はマニフェストと異なり**人間が手書き**する。マニフェスト自動生成の原則（§15.1）を崩さないための代償として受け入れる。

## 5. 議題1: グルーピング

### 移植性

主要3形式すべてにネイティブな表現があり、変換は素直なマッピングになる。

| 形式 | 表現 |
|---|---|
| SFZ | `group=N` / `off_by=N` / `off_mode=fast` |
| UVI Falcon | キーグループの mute group / exclusive |
| KONTAKT | Voice Group または Group Start Options（スクリプト経由） |

グループは整数IDの割り当てにすぎず、検証も「同一グループのメンバーが実在するか」程度で済む。実装コストは低い。

### 収録時に考慮すべき非可逆要素

排他関係そのものは後付けできるが、**`release_capture` は後から伸ばせない**。ドラムキット1台を1つの `sampling_definition` で収録すると `note_on` / `release_capture` がキット全体で共通になり（§7.6、§10.1）、オープンハイハットやシンバル系の減衰が切れた場合は再録音となる。

対策（いずれも現行仕様の範囲内で今すぐ実行可能）:

1. `release_capture` をキット内で最も減衰の長い音に合わせて長めに取る。余剰の尾部はポストプロセスの `trim` ステージが落とすため実害はない。
2. キットを楽器グループ単位で別 `id` の `sampling_definition` へ分割する。§7.2 が「同じMIDI音色を異なる条件で収録する場合は異なる `id` を使用できる」と明示している。

2 を採ると排他グループが**音色単位の属性**となり、後付け定義が `exclusive_groups: [{ name: hihat, tones: [...] }]` とさらに単純になる。将来を楽にする選択肢として記録しておく。

## 6. 議題2: リリーストリガー

2つの異なる話が混在しているため分離して判断する。

### (a) ノートオフで別サンプルが鳴る（一般的なリリーストリガー）

ピアノのダンパーノイズ、ギターのフレットノイズ、チェンバロのジャック戻り音など。

| 形式 | 表現 |
|---|---|
| SFZ | `trigger=release` + `rt_decay` |
| UVI Falcon | キーグループのリリーストリガー |
| KONTAKT | on-release のグループスタートオプション |

**すべて宣言的に表現可能。** 実質「別音色をもう1セット録る」だけであり、後付けは容易。定義ファイルの追加は §4 の `release_triggers:` 数行に収まる。

現実的な制約として、SC-8850 のようなハードウェア音源はリリースノイズを独立に発音できないことが多く、そもそも収録対象になりにくい。実用上は外部素材や別途収録した素材を組み込む口として設計することになる。

### (b) サンプル再生の終了を契機に次のサンプルを鳴らす（連鎖）

**仕組み化しないことを推奨する。**

理由は複雑さではなく、**移植先に共通の表現が存在しないこと**にある。SFZ には「サンプル終端」をトリガーとする opcode がなく、`delay` による近似か Falcon / KONTAKT のスクリプトに頼るしかない。ここを汎用的にモデル化すると「定義ファイルには書けるがエクスポータの大半が実装できない」状態になる。

対処方針: 対応形式が共通して持つ機能の範囲（= (a) + 遅延）までを共通モデルとし、それを超えるものは形式固有のエスケープハッチ（生 opcode / スクリプト片の埋め込み）へ逃がす。これも後から追加できる。

### 複雑さについての見解

「定義ファイルと制御プログラムが余計に複雑になるか」の答えは**置き場所によって変わる**。

- `sampling_definition` の中に入れる場合: **高くつく。** ゾーン×ベロシティの直積モデル（§10.1）、ファイル名テンプレート（§11.4）、マニフェストの `samples` 配列、ハッシュ対象のすべてに「録音とは無関係な概念」が侵入する。
- 第3レイヤーへ置く場合: **録音側の複雑さは増えない。** 増えるのは (1) 人が書くYAMLが1枚増えること、(2) エクスポータ内のマッピング処理のみ。しかも実際にそうしたキットを作るときにだけ支払うコスト。

## 7. 決定事項

- [x] サンプリング作業は現行実装のまま進行してよい。両ケースとも録音成果物には影響しない。
- [x] 録音済みマニフェストへの後からの追記は禁止（2種類のハッシュ連鎖が壊れるため）。
- [x] 排他グループ・リリーストリガーは、将来のエクスポート層（第3レイヤー）で表現する方針とする。
- [x] (b) の連鎖トリガーは汎用機構化せず、スコープ外とする。
