# ループ継ぎ目のクロスフェードによるクリックノイズ軽減

日付: 2026-08-11

## 1. 議題

> 現状波形そのものには加工を行わない実装になっていると思いますが、クロスフェードをさせることで不自然さ（クリックノイズ）を軽減することはできる？

## 2. 現状の確認

既存実装は仕様どおり完全に非破壊であり、`data` チャンクの波形には一切手を加えていない。

| 箇所 | 挙動 |
| --- | --- |
| `src/sample_loop_detector/audio/decoder.py` | 解析用に `float64` へデコードするのみ。書き戻さない。 |
| `src/sample_loop_detector/pipeline.py` の `write_output_wav` → `src/sample_loop_detector/audio/riff.py` の `insert_smpl_chunk` | 元の生チャンクバイト列を保ったまま `smpl` チャンクを `data` の前に差し込むだけ。 |
| `src/sample_loop_detector/audio/preview.py` | コードベース唯一の `soundfile.write`。試聴用の補助ファイルであり、`smpl` 出力には影響しない。 |

仕様書上の位置づけ:

- §3.3 対象外 — 「破壊的なクロスフェード加工」
- §16.1 — 「MVPでは、このクロスフェードを出力WAVの`data`チャンクへ焼き込まない」
- §20 WAV書き込み時の非破壊要件 — `data` チャンクのバイト同一性、`float64` 再エンコードの禁止
- §33 エージェントへの実装上の注意 — `soundfile.write` によるファイル全体の再生成はアンチパターン
- §34 将来拡張 — 「破壊的クロスフェードの焼き込み」

つまり焼き込みは**設計上意図的に除外された領域**であり、拡張候補として明記されている。

## 3. 結論

**軽減できる。ただし `data` チャンクへの破壊的な焼き込みが前提。**

根拠:

- `smpl` チャンクはループ点しか保持できず、クロスフェード長を伝えるフィールドを持たない（§16.5 に「出力する`smpl`チャンクはクロスフェード情報を保持しない」と明記）。
- 再生側のサンプラーは `end → start` を**ハードシーム**でつなぐため、メタデータだけではクリックノイズは消えない。
- WAV 単体で完結させるなら波形を書き換えるしかない。
- ただし Kontakt など一部サンプラーは独自のループクロスフェードパラメータを持つため、`best_crossfade_ms` を推奨値として提示し仕上げを再生側に任せる運用も成立する。

## 4. 焼き込み方式（重要な技術的知見）

### 既存の評価用レンダラは焼き込みに転用できない

`src/sample_loop_detector/analysis/render.py` の `render_crossfaded_repeats` は **overlap-add** であり、実効ループ周期が `L - crossfade` に縮む。再生時の連続クロスフェードを模した評価モデルとしては妥当だが、静的な WAV へ焼き込む処理とは幾何が異なる。

**したがって `evaluate_crossfade` のスコアは焼き込み結果の予測としてはズレる。** 焼き込みを実装する際は、方式に合わせた評価関数を別途用意する必要がある。

### 採用方針: プリロール方式

サンプルエディタ標準のループクロスフェード。

```text
S = loop start, E = loop end, N = crossfade samples

         [S-N .. S-1]   pre-roll（原音のまま残る）
              |
              v  fade_in
  ... ####|============|######
          E-N+1        E
              ^  fade_out

result[E-N+1+i] = audio[E-N+1+i] * fade_out[i]
                + audio[S-N+i]   * fade_in[i]
```

- `i = N-1` のとき `result[E] == audio[S-1]` となる。よって `E → S` のジャンプが**原波形の自然な連続そのもの**になり、継ぎ目が原理的に消える。
- 書き換え範囲は `[E-N+1, E]` のみ。ループ長 `E-S+1` は不変。ループ開始位置より前は無傷。
- 前提条件: `S >= N`（アタック部に `N` サンプル以上の余裕）。
- フェード曲線は既存の `crossfade_curves()`（コサイン、§16.3）をそのまま再利用できる。

### 対案: ポストロール方式（今回は第一候補としない）

リリース部の素材をループ先頭へフェードする鏡像方式。書き換え範囲は `[S, S+N-1]`、`result[S] == audio[E+1]` となる。条件は `E+N < 総サンプル数`。

## 5. クロスフェードの効果と限界

| 分類 | 内容 |
| --- | --- |
| 直せる | 振幅段差・一次微分段差によるクリック（`amplitude` / `derivative` コスト） |
| 緩和 | 位相ズレ由来の歪み |
| 直せない／悪化しうる | 位相不一致によるコムフィルタ的な打ち消し（音量ディップ）、レベルのパンピング、ビブラート/トレモロ位相のスミア、音色変化の連続性 |

素性の悪いループ点をクロスフェードで救うことはできない。これは §16.5 の「クロスフェード評価だけが良好な候補を採用してはならない」「クロスフェード後のスコアが良好でも、ハードシームスコアが既定の上限を超える場合は不採用とする」という規定と整合する。

現在の役割分担（良いループ点を出す → `best_crossfade_ms` を推奨値として提示 → 仕上げは利用者側）は妥当と判断した。

## 6. 将来実装する場合の障壁

- **エンコーダが存在しない。** `float64` → 元ビット深度の PCM バイト列への変換が未実装（`decoder.py` はデコードのみ）。16/24bit ではディザ要否の判断も必要。
- **§20 のバイト同一性保証と衝突する。** 焼き込みは既存の出力パスを汚さず、`--bake-crossfade OUT.wav` のような**別ファイル出力**とすべき。
